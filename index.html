CASE 05 · CYBER RESILIENCE

Whodunnit: a vibe-coded game, then hardened

A free murder-mystery logic game with player accounts, a daily case and a global leaderboard, built end to end with an AI coding assistant. Getting it working was the easy part.

A security review against the live database found that player emails were stored in plain text and that nothing slowed down repeated sign-in or sign-up attempts. Both were fixed the same day, and the gaps that remain are listed below rather than hidden.

The lesson: AI makes an online game easy to ship, but security has to be asked for and then checked. It does not arrive by default.

Password hashing Breached-password check Rate limits Data minimisation Security headers Known limits disclosed

What the security review changed

BeforeAfter
Emails stored in plain textOnly a keyed hash is stored; the key is kept outside the database
No limit on attempts from one connectionSign-in and sign-up are rate limited; addresses are kept only as hashes
Password hashing below the OWASP minimumRaised to OWASP settings; old hashes upgrade at next sign-in
Known-breached passwords acceptedRefused, using Have I Been Pwned without sending the password
No browser security headersStrict content security policy, HSTS and frame blocking

Six things any vibe-coded game must get right

Passwords

Never stored. Salted, deliberately slow hashes, a lockout after repeated wrong guesses, and breached passwords refused.

Personal data

Keep as little as possible. Emails are hashed, and the leaderboard shows display names and scores only.

Sign-in answers

The same reply, taking the same time, whether the email is unknown or the password is wrong.

Sessions

Signed tokens that expire. Google sign-ins are verified against Google's own keys.

Database

The browser never holds a database key. Row-level security is on, and public roles have no access.

Abuse and the browser

Rate limits on accounts, plus headers that stop injected scripts, framing and downgrade to plain HTTP.

Encrypted is not the same as safe

The database provider encrypts its disks and all traffic uses TLS. That protects against a stolen disk, not against someone holding the project's keys. Hashing the emails is what protects them in that case.

Still not solved

  • A single server secret protects email hashes and sessions. It is the weakest point, and rotating it signs everyone out.
  • Session tokens live in browser storage, and there is no "sign out everywhere" yet.
  • Sign-up still reveals whether an email already has an account; rate limits only slow this down.
  • With hashed emails the game cannot email players; password reset still needs an email service.
